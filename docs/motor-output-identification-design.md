# モータ直接出力の確認と B_m 同定の設計案

状態: 段階A〜Cの確認用ソフトウェアを実装済み・実機未確認。作成日: 2026-10-22、更新日: 2026-10-23。

実行方法と現在の実装範囲は [確認用ノードの手順](motor-output-probe.md) を参照する。
段階D/Eの接地実験・モデル解析とDOBは、段階A〜Cの実機確認後に実装する。

VS-WRC201 のファームウェアは変更せず、公開された I2C レジスタの設定で
位置P制御の寄与を外し、Raspberry Pi から駆動出力を指定できるか確認する。
成立した場合に限り、駆動出力から車輪角速度へのモデルを同定し、将来の
外乱オブザーバ（DOB）による制御に使う。本書のモード名・項目名・ファイル名は
設計を表す。実装済み部分の操作は上記の手順にまとめる。

## 1. 制御を変更する場所

現状は以下の二段構成になっている。

```text
rover_drive の v, omega
  -> Python の pos_controll(): 加減速制限と位置増分の生成
  -> A_POS に書き込み、TRIG で T_POS に加算
  -> 基板内の位置P制御・出力補償
  -> モータ -> エンコーダ
```

確認したい構成は以下である。

```text
Pi 上の試験入力列（将来は DOB 制御則）
  -> 出力の制限と整数化
  -> T_OUT に書き込み
  -> 基板内の出力処理〔位置Pゲインとパンチはゼロ〕
  -> モータ -> エンコーダ
          M_OUT を読み、基板の計算出力を確認
```

`VsWrc201Motor.pos_controll()` の戻り値だけを変更しても、この構成にはならない。
`controller.py` にある位置増分の書き込み経路と、起動時の基板設定も変更対象になる。
最初の実装は専用の試験ノードに分け、通常走行の既定経路へ DOB を導入しない。

## 2. 公開仕様と、実機で確かめる仮説

メーカーの [メモリマップ](https://vstoneofficial.github.io/lightrover_webdoc/Tips/memMap/)
には以下のレジスタが記載されている。

| 用途 | motor0 / motor1 のアドレス | サイズ |
| --- | --- | --- |
| 出力 Enable | `0x10`、bit 0 / bit 1 | 1 byte |
| 位置比例ゲイン FB_PG | `0x20` / `0x22` | 各2 bytes |
| 出力上限 FB_OLIM | `0x2c` / `0x2e` | 各2 bytes |
| パンチ FB_PCH | `0x30` / `0x32` | 各2 bytes |
| 位置目標 T_POS | `0x40` / `0x44` | 各4 bytes |
| 出力オフセット T_OUT | `0x50` / `0x52` | 各2 bytes |
| 実測位置 M_POS | `0x60` / `0x64` | 各4 bytes |
| 計算出力 M_OUT | `0x6c` / `0x6e` | 各2 bytes |
| ウォッチドッグ WDT | `0x08` | 2 bytes |

位置Pゲインにゼロを指定できることはメーカーの
[パラメータ説明](https://vstoneofficial.github.io/lightrover_webdoc/Tips/adjustMParam/)
で確認できる。一方、次の事項は現時点では仮説または未確認事項である。

- Pゲインとパンチをゼロにすると、T_OUT で符号付きの駆動出力を指定できるか。
- T_OUT と M_OUT の関係、倍率、符号、更新遅れ、出力制限の適用順序。
- T_POS と M_POS に差があっても、Pゲインゼロならその差が出力に影響しないか。
- WDT の期限切れ時の停止、再設定・再 Enable の条件。
- メーカー版 I2C サービスの負数の送信方法、読み取り値の符号解釈、バイト順。

M_OUT の `0x1000` は仕様上100%に対応するが、T_OUT に同じ換算を適用できるかは
確認する。M_OUT はファームウェアの計算結果であり、電流・トルク・端子電圧の
実測値でも、モータが回転した保証でもない。レジスタ読み戻しの一致と、M_OUT の
応答と、エンコーダの応答を別々に評価する。

## 3. 実装を進める段階と判定

| 段階 | 実施内容 | 次に進む条件 |
| --- | --- | --- |
| A: 通信・設定確認 | 出力禁止中に読み書き、符号、設定保存・復元を確認 | 負数を含む値の扱いと復元を確認できる |
| B: 直接出力の確認 | 車輪を浮かせ、ゼロと小さな正負出力を与える | T_OUT、M_OUT、回転方向の関係が説明できる |
| C: 停止と独立性の確認 | WDT停止、位置目標への依存、制限値の作用を確認 | 外部の出力更新が止まったときの停止と、位置Pの寄与がないことを確認できる |
| D: 同定実験 | 接地条件で定常入力・過渡入力を収集 | 欠落や飽和を分離した入出力データが得られる |
| E: モデル検証 | 別入力列でゲイン・動特性を検証 | 誤差と使用可能な入力域・帯域を説明できる |

段階B/Cで仮説が成立しなければ、同定やDOBへ進まず結果を文書化し、メーカーに
レジスタの作用を確認する。ファームウェア改変や別の出力経路へ自動的に切り替えない。

試験ノードは `DISABLED -> CONFIGURING -> READY -> RUNNING -> RESTORING -> DISABLED`
の状態を持つ。異常時は `FAULT` へ遷移し、自動で `RUNNING` に戻らない。
起動しただけでは `READY` を越えず、確認済みの有限入力列の開始操作を必要とする。
入力とパラメータの非有限値・範囲外・時刻逆行は出力前に拒否する。

### 3.1 試験ノードの起動と設定

通常の位置指令ノードを停止し、出力を扱うノードを一つにする。通常の
`tracedPosController.py` とメーカー版 `pos_controller.py` の両方が停止していることを
確認する。別の ROS ノード名を使うだけでは I2C の競合を防げない。
試験ノードは同一Pi上の共有プロセスロックで試験ノードの二重起動を防ぎ、既知の
通常制御ノードとの同時起動を検出した場合は開始しない。ただし、協調しない
I2Cクライアントをこのロックで排除できるとは扱わない。

起動手順は以下とする。いずれも一つのI2C操作列として直列に実行する。

1. 出力禁止 `O_EN=0` を指示し、読み戻す。
2. 変更対象のPゲイン、パンチ、出力上限、T_OUT、WDT等を読み、復旧用スナップショットを
   Piのローカルファイルへ保存完了してから設定変更へ進む。システム名、ファームウェア
   リビジョン、車両識別子、boot_id、採取時刻も含め、PC側のROSログにも出す。
3. T_OUT を両輪ゼロに設定する。
4. Pゲイン・パンチを両輪ゼロにし、試験用の出力上限を設定して読み戻す。
   加速度関連レジスタ等を追加で変更する必要が出た場合も、作用確認後に保存・復元の対象とする。
5. 負数のシリアライズと読み戻しを出力禁止中に確認する。最後に T_OUT をゼロへ戻す。
6. 段階B/Cの微小出力試験用、または確認済みの段階D用の設定を明示的に選んで出力を許可する。

出力上限はゼロ以外の実験設定として明示する。未指定なら出力を許可しない。
公開表にある初期値が実機の現在値だとは仮定しない。

### 3.2 出力と位置偏差の関係の確認

車輪を浮かせ、ゼロ、正方向、ゼロ、負方向、ゼロの短い入力列を片輪ずつ与える。
最初は十分小さい範囲から始め、M_OUT の変化と回転を見ながら段階的に入力域を調べる。
回らなかった区間も保存し、デッドゾーンの候補として扱う。

T_OUT の反映に A_POS 加算用の TRIG が必要だとは仮定しない。まず T_OUT の書き込みだけで
反映されるか確認する。通常走行の位置増分書き込みやトリガを試験中に混在させない。

Pゲイン・パンチゼロの状態で、出力禁止中に小さな異なる T_POS を設定し、同じ T_OUT に
対する M_OUT を比較する。T_OUT=0 なら出力がゼロになることも確認する。
この結果から、位置偏差を変えても出力が変わらないかを評価する。

負数を扱う際は、サービスの生の readData と、16 bitの2の補数として解釈した値の両方を
記録する。M_POS は32 bitの巡回カウンタとして差分を求める。

### 3.3 停止と通常運転への復帰

直接出力は最後の指令が残る可能性があるため、試験入力には有限の有効期限と
総実験時間を持たせる。初回は車輪を浮かせ、出力更新停止時の挙動を確認する。

WDT は公開仕様では `0` が無処理、`0xffff` がモータ停止、それ以外がmsのカウントダウン
である。実機で期限切れ停止と再始動条件を確認するまでは、接地した直接出力試験を行わない。
WDT更新間隔・期限・指令期限は実測したI2C所要時間と出力周期から決め、設定として記録する。
出力操作とWDT更新は単一ワーカーで処理し、故障後に別スレッドがWDTだけを更新し続ける
構成にしない。Pythonの終了処理だけに停止を依存させない。

指令期限切れ、I2C失敗、エンコーダ更新停止、設定不一致、総実験時間超過で故障状態へ遷移し、
非ゼロ出力の更新とWDT更新を止める。通信できる場合は出力禁止を優先し、T_OUTゼロも
試みる。通信要求の成功は実機停止の保証ではない。失敗した要求を盲目的に再送したり、
自動的に再 Enable したりしない。左右の書き込みは非原子的で、片輪だけ更新された故障も記録する。

正常終了時は出力禁止を確認してから T_OUT をゼロにし、保存したPゲイン・パンチ・
上限等の設定を復元して読み戻す。元が非ゼロの T_OUT でも、その値や元の Enable 状態は
自動復元しない。モータ出力は無効のまま終了する。

異常終了後も含め、通常ノードを再起動する前には復旧処理で T_OUT両輪ゼロ、通常用の
Pゲイン・パンチ・上限、WDTの通常設定を確認する。現行コードはWDTを設定しないため、
復帰時は無処理の0を明示する。現行の通常初期化は
T_OUTを消去しないため、通常ノードの再起動だけでは復旧完了とみなせない。
復旧スナップショットがない場合は、明示的な通常設定を使い、値を推測しない。

## 4. 入出力の定義

保存時の車輪配列は既存ログと同じ `[motor0, motor1]` とし、基板の符号を保存する。
解析時だけ、確認した物理的な左右対応と符号を行列 S で変換する。

```text
u_requested -> 制限 -> 整数 T_OUT -> 基板内処理 -> M_OUT -> 車輪回転
```

T_OUTとM_OUTの倍率が一致すると確認できた場合、駆動入力を

\[
u_{\mathrm{board},i}=q_i/4096
\]

と定義する。q は制限・整数化後に書き込むT_OUT値である。入力は無次元、車輪角度はrad、
B_m の単位は rad/s とする。不一致なら、測定した換算をモデルに明記する。
要求値と制限後の値を混同せず、同定には制限後の入力を用いる。

M_OUT/4096 は基板計算出力の観測値として併記する。T_OUTからM_OUTまでに無視できない
遅れ・制限があれば、指令から車輪までのモデルへ残す。M_OUTを入力にしたモデルを別に
推定する場合は、T_OUT入力のモデルとは別名で保存し、制御器へ無条件に流用しない。

角度は巡回補正したエンコーダ差分を積算し、現在の換算係数
`N_enc = 1188.024 count/turn` を使って `2*pi/N_enc` を掛ける。
S は角度と駆動入力の両方へ一貫して適用する。メモの `[R,L]` とログの並びを
コードの変数名だけで決めない。

## 5. 追加する記録

### 5.1 既存の記録の再利用

[現在のログ](drive-trace.md)には M_POS の生カウント・差分、読み取りごとのI2C開始/終了時刻、
boot_id、run_id、イベント連番がある。これらを使う。現行の increment_counts は
位置目標への加算値であり、新しい駆動出力の項目へ名前を流用しない。

新しい試験ノードも `drive_trace/controller` とその metadata/timing に出す。
車輪側は既存の `drive_trace/wheel` を使い、既存の DriveTraceRecorder の6トピックで収集する。
イベント名とメタデータで通常の位置増分ログと区別する。

### 5.2 新しいイベント案

| イベント | 記録する内容 |
| --- | --- |
| `output_probe_state` | 試験識別子、状態、段階、遷移理由、実験区間番号 |
| `output_configuration` | 設定前の値、設定要求、読み戻し、確認結果、全サービス呼び出し |
| `output_command` | 指令連番、希望時刻、実時刻、要求値、制限後T_OUT値、制限理由、左右の書き込み成否・時刻、WDT更新 |
| `output_readback` | T_OUT・M_OUT・O_EN・必要な診断値の生値/解釈値、全読み取り時刻、対応する指令連番 |
| `output_restore` | 出力禁止、ゼロ化、設定復元の要求と確認、未復元項目 |

M_POS は wheel イベントと時刻で結び付ける。M_OUT取得前に次の出力へ進んだ場合も、
実際の操作順から対応を復元できるようにする。異なる時刻の値を同時刻測定と表示しない。

メタデータには以下を含める。

- `controller_model=output_probe`、入出力単位、車輪順序・符号・換算、ログ項目の版。
- ファームウェアリビジョン、保存設定、試験設定とその読み戻し結果。
- 出力上限、WDT期限、指令期限、出力/追加読み取りの周期、実験入力列と乱数seed。
- 床・搭載条件・車両識別子。バッテリー電圧は取得できれば低頻度の別診断として記録する。
- 新規の試験・出力モジュールも含むソースハッシュ。現行 source_hashes() の固定4ファイルだけでは不足する。

T_OUT・M_OUT等の追加読み取りは試験モードだけで有効にする。
段階B/Cでは各入力の前後に読み、段階Dでは動特性を判別できる頻度を実測で決める。
I2C負荷と観測周期をログに残し、読み取りが応答を変えていないか確認する。

試験ログは full を必須にし、初期化失敗で NullTrace へフォールバックした場合は実験を開始しない。
既存の通常走行では、ログ故障時も走行を継続する従来方針を維持する。
PCでの確実な保存はROSログだけでは保証できないため、解析時に欠落を検査する。

## 6. B_m と動特性の同定

### 6.1 入力列

最初に車輪を浮かせて通信・符号・停止を確認し、同定本番は実験と同じ床・搭載条件で行う。
低・中・高の3～5段階の正負出力を、整定を確認できる時間だけ保持して繰り返す。
保持時間は予備試験で得た時定数の4～5倍を目安に調整する。

直進だけで左右入力を常に連動させない。片側を一定にして他方を変える区間を含める。
次に一定回転付近の小振幅の多段入力または独立したランダム入力を用いて過渡応答を取る。
ゼロ近傍・方向反転は摩擦等の別評価区間とし、広い入力域を一つの線形ゲインに押し込まない。

### 6.2 静的モデル

整定した区間では角度の差から平均角速度を求める。

\[
\bar\omega_i=\frac{\varphi_i(t_b)-\varphi_i(t_a)}{t_b-t_a},
\qquad \bar\omega=B_m\bar u+c.
\]

切片 c を含む最小二乗推定から始め、まず左右対角のB_mを推定する。
交差項を含む2入力モデルは、独立な入力を与えたデータで必要性を確認してから使う。
入力行列のランクと条件数を確認する。正負で差があれば方向別の傾き・切片を保存する。

d_k を時刻ごとに自由な未知量にするとB_mの誤差と区別できないため、同定では
負荷条件を揃え、一定負荷を切片、残りを残差として扱う。B_mの誤差をDOBがすべて
吸収できるという前提で同定精度を評価しない。

### 6.3 動的モデルと検証

各輪の候補を次の一次遅れ＋むだ時間とし、必要なら二次モデルと比較する。

\[
G_i(s)=\frac{b_i}{\tau_i s+1}e^{-L_i s}.
\]

このとき低周波近似のB_mの対角要素は b_i である。離散モデル
`omega[k+1] = A omega[k] + B u[k] + c` を使う場合、定常ゲインは
`(I-A)^(-1) B` であり、離散状態方程式のBをそのままB_mと呼ばない。

推定には実際の書き込みと読み取りの単調時計時刻を使う。サービスの往復区間内の
実適用時刻は確定できないので、その時間幅も残す。PC受信時刻を入出力時刻にしない。
エンコーダ差分を取得した時間窓と入力保持区間を対応付ける。等間隔へ再標本化する場合も、
位置増分と入力の保持を保ち、欠落をゼロで埋めない。入力失敗やノード再起動で区間を分ける。

モデルの検証は別の実験入力列で行い、角速度と積分した角度の両方を比較する。
定常誤差、過渡の誤差、応答遅れ、残差と入力の相関、試行間のばらつきを報告する。
飽和・未整定・読み取り異常・欠落区間は区別し、採否と理由を保存する。
実機の将来性能をシミュレーションの適合度だけで保証しない。

成果物は B_m、切片、正負/入力域による差、時定数、遅れ、推定のばらつき、
使用データの識別子と使用可能な条件を含むモデルファイルと図とする。
定数B_mを使う帯域で遅れ・位相差が許容できなければ、DOB側の対象モデルを拡張する。

| `tests/test_motor_output_probe.py` | 偽サービス・偽時計による状態遷移と故障処理の確認 |

上記src/scripts/launch/configは `harada-tsubakino/` 以下とする。
新規スクリプト・configをCMakeの配置対象へ追加する。
通常の `harada-tsubakino.launch` の既定動作とメーカーのI2Cサーバー実装は維持する。
試験用Launchは通常Launchを丸ごとincludeせず、I2Cサーバーを重複起動させない。
試験の有限入力列はPiで実行し、MATLAB側の配信時刻を実験の入力時刻とは扱わない。

現行の通常ログの仕様と、試験モードで追加する読み取り・停止処理を文書上でも区別する。
DOB実装時にはこの出力層を再利用し、位置増分出力とは明示的に分岐させる。
`rover_drive` の速度指令をデューティ比として再解釈する変更は行わない。

## 8. 検証と実装順序

1. 段階A～C用の出力層、設定スナップショット、復旧、fullログ、専用Launchを実装する。
2. 偽サービスで設定不一致、負数、片側書き込み失敗、読取失敗、期限切れ、復元失敗を確認する。
   非ゼロ出力が設定確認より先に出ないこと、故障後にWDT更新と非ゼロ出力が継続しないことも確認する。
3. 既存の走行回帰テストを実行し、試験モードを使わないときの計算とI2C要求を確認する。
   Python 2 / ROS Melodicの実行互換性とcatkin配置はPiで別途確認する。
4. 実機で段階A～Cを実施し、T_OUTとM_OUTの関係・停止・復旧の結果を本書へ追記する。
5. 成立した範囲に合わせて段階Dの入力列と解析を実装し、別データでモデルを検証する。
6. 得られたモデルでDOBを検討する。符号修正、推定帯域、入力飽和時の扱いは別設計として詰める。

ブランチは実装・検証した変更を `feature/drive-system-identification` に載せてプッシュする。
段階A～Cの確認用実装と、実機確認後の同定/DOBを別の変更単位にする。
本設計書の作成は、実機で直接駆動が成立したことや、ファームウェアを書き換え可能なことを意味しない。
